# Vendored engine provenance

The files in this directory are vendored from the `kontell/jellyfin` fork,
branch `integration/syncplay-phase1` @ `336ac05456` ("SyncPlay protocol v2:
versioned state, snapshots, beacons, WS time sync, reconnect grace"), whose
SyncPlay sources are byte-identical to `release-10.11.z` @ `1fbd873929`
(10.11.11) outside the phase-1 changes — verified before vendoring.

Keep divergence deliberate: upstream SyncPlay changes in server releases are a
review trigger (`git diff <old> <new> -- Emby.Server.Implementations/SyncPlay
MediaBrowser.Controller/SyncPlay MediaBrowser.Model/SyncPlay` in the server
repo), and these files are the future upstream PR series, so gratuitous edits
here make the eventual upstreaming harder.

| `Group.cs` | `Emby.Server.Implementations/SyncPlay/Group.cs` | plugin namespace; implements `IGroupStateContextV2`; ctor takes `Sender` + `ProtocolVersionRegistry`; `AddSession` reads the registry instead of `request.ProtocolVersion`; `SendGroupUpdate`/`SendCommand` translate stock typed updates to wire DTOs at the choke point and deliver via member `Session` refs; `GroupJoined`/`StateSnapshot`/`PositionBeacon` built as wire DTOs directly (`GetWireInfo` is member-scoped per the §5.2 advertisement rule); `GetInfo()` reverted to the stock 5-arg `GroupInfoDto` (interface surface). **Fix divergence: null-guarded item lookups** — `GetItemById` answers null for an unknown or deleted id, and all six upstream call sites dereferenced it unguarded (`#nullable disable` hides it): an item deleted while sitting in an active group's queue NRE'd inside the group lock, and in `NextItemInQueue` the NRE fired *after* the queue pointer advanced, splitting the group's index from every client's view. Upstreamable as-is. **Fix divergence: the position clamp treats `RunTimeTicks == 0` as unbounded** (`SanitizePositionTicks` delegates to plugin-owned `Positions.Sanitize`) — a runtime of 0 is what a live TV channel, a deleted item or an external-content entry produces, and upstream's `Math.Clamp(ticks, 0, 0)` zeroed every Seek and Ready report, leaving the member permanently "lost in time". Also the G3 groundwork: external-content descriptors carry runtime 0 legitimately (`docs/syncplay-generic-backend-plan.md` in plugin.video.kofin, G3.1). **Feature divergence: external content (G3.3)** — a `Content` table (plugin-owned `ContentTable`) rides beside `PlayQueue`: descriptor entries travel the stock queue as fresh sentinel GUIDs, `HasAccessToQueue` skips registered sentinels (validated at registration; resolvability is the members' problem by design), and the five runtime sites source through `ItemRunTimeTicks` — table first (a registered 0 is a real answer: unbounded), library second. **Feature divergence: content on the wire, capability-gated (G3.4)** — `SendGroupUpdate<T>` enriches a `PlayQueueUpdate` per entry (`WirePlayQueueUpdate`) for members whose device declared the `ExternalContent` capability and keeps the stock shape for everyone else; `GetSnapshot(bool)` does the same for the snapshot's queue; `AllUsersHaveAccessToQueue` vetoes a descriptor queue unless every member's device declared the capability (the access analog for content the server cannot resolve); `CanRepresentQueue` is the visibility test the manager's join/list/get gates call. **Feature divergence: rendezvous** — `ShouldRendezvous`/`RendezvousMember` hand a member the hot-join path instead of correcting it again — from the correction branch when the corrections are not converging, and from the wait timeout, which measurement showed is the only one of the two a slow-reloading member actually reaches; `SetBuffering(.., false)` resets the correction counters; `IsIgnoredByTimeout` (interface surface, for the state machine's recovery path) **Fix divergence (#14)**: `IsSpectator` and `RestartWaitFor` (interface surface for the state machine) — the latter resumes waiting for a timed-out member through `GroupMember.ResumeWaiting` and restamps `BufferingSince`, which `SetBuffering(.., true)` leaves alone for a member still flagged buffering from the stall the group gave up on. **Fix divergence: a group-wide wait restarts every member's clock** — `SetAllBuffering(true)` (Play, SetPlaylistItem, Unpause from Idle, Seek, Next, Previous) stamped `BufferingSince` only on a false-to-true transition, so a member already buffering when the new wait began kept its old timestamp and the wait-timeout sweep could give up on it as the new wait started. **Feature divergence: the load/stall timeout split** — `SetAllBuffering(true)` marks every member `BufferingForLoad` when the group changed or restarted the item (`_itemLoadPending`, set by `SetPlayQueue` and `RestartCurrentItem`, and cleared when the request that set it has been handled (and at the end of `CreateGroup`, which is not a request), so a change that starts no wait — removing the playing entry keeps the state — cannot hand the load timeout to a later Seek); a seek within the loaded item is not a load and keeps the stall timeout, as before. A member that reports ready is no longer loading (`BufferingForLoad` clears). A member that starts buffering on its own is a stall; a joiner the states mark buffering is a load (`MarkJoinerLoading`). `GetStalledMembers` returns each stalled member with the timeout it outlived; `GetStalledBufferingSessions(timeout)` is kept as the single-timeout form. **Feature divergence: diagnostics** — the constructor takes the plugin-owned `Diagnostics/EngineCounters` (optional; a private set when omitted) and counts where the engine already logs: hot joins and rendezvous separately (both go through the private `StartCatchUp`, which `BeginHotJoin` wraps), disconnections (once per death, though `SessionEnded` and the liveness sweep can both report it), reconnections (`TouchSession` and `ReconnectSession`), corrections (`RecordCorrection`, interface surface). `_stateSince` records when the state last changed; `GetDiagnostics` builds the read-only, plugin-owned `GroupDiagnostics`. `GetStalledMembers` also returns whether each member was loading, so the sweep can count the two timeouts apart. |
| `SyncPlayManagerV2.cs` | `Emby.Server.Implementations/SyncPlay/SyncPlayManager.cs` | plugin namespace; class renamed; implements `ISyncPlayManagerV2`; ctor takes `Sender` + registry (passed to groups); adds `ListGroupsDetailed`; error updates stay on the stock `ISessionManager.SendSyncPlayGroupUpdate` path (StateVersion 0 by design). **Feature divergence: external content (G3.3)** — `HandleRequestWithContent` registers sentinel-keyed descriptors on the session's group under its lock, dispatches through the stock path, and prunes the table to the resulting queue (a refused request included). **Feature divergence (G3.4)**: the join, both lists and GetGroup additionally gate on `Group.CanRepresentQueue(session)` — a descriptor group is invisible and unjoinable to a device without the capability, byte-for-byte the UX stock gives a queue a user cannot resolve. **Feature divergence: rendezvous on wait timeout** — `IgnoreStalledMembers` rendezvouses a v2 member instead of merely ignoring it, so the group stops waiting *and* the member is given a scheduled catch-up; v1 members are abandoned as before **Feature divergence: configurable timings, and a load timeout** — the four timing constants are read from the plugin configuration on every use (plugin-owned `Configuration/EngineTimings`, clamped), and the wait timeout is split: `IgnoreStalledMembers` asks `Group.GetStalledMembers(stall, load)`, which applies `LoadTimeout` (default 30 s) to a member loading an item at the group's request and `StallTimeout` (default 10 s, the old constant) to everything else. Measured on a 12.1 server: starting a HEVC item, both jellyfin-web members outlived the 10 s wait while loading and the group went to Playing with nobody ready. **Feature divergence: diagnostics** — ctor takes `EngineCounters` (DI singleton, passed to every group); counts load vs stall timeouts in the sweep, buffering-grace recoveries (`CancelDeferredBuffering` now answers whether it cancelled one) and applications, and grace expiries; `GetDiagnostics` (interface surface) collects every group under the usual locks for the admin-only `GET /SyncPlay/V2/Diagnostics`. `SocketLiveness` counts dead sockets. |
| `GroupMember.cs` | `MediaBrowser.Controller/SyncPlay/GroupMember.cs` (fork version) | plugin namespace; `HotJoining`; `CorrectionAttempts` + `LastCorrectionDelayTicks` for the rendezvous decision; `ResumeWaiting()` — the one place the "the group waits for this member again, without reversing a spectator choice of its own" rule lives, called from `SetBuffering`, `ReconnectSession` and the state machine's recovery path, which had two inline copies of it between them; `BufferingForLoad` for the load/stall timeout split |
| `GroupStates/*.cs` | `MediaBrowser.Controller/SyncPlay/GroupStates/*.cs` (fork versions) | plugin namespace + `using` for the stock parent namespace; `WaitingGroupState` casts the context to `IGroupStateContextV2` for `GetMemberPlaybackOffset` (upstream: interface member). Vendored wholesale because the states hard-construct each other, so partial vendoring cannot work. **Feature divergence (beyond the fork): hot join** — `PlayingGroupState.SessionJoined` keeps the group Playing for v2 joiners (`BeginHotJoin`: not-waited-on flags + snapshot push), their `Buffering` is absorbed, and their `Ready` is answered with a private scheduled `Unpause` at the live position (`CompleteHotJoin`); v1 joiners keep the classic barrier. Config-gated (`HotJoin`, default on). The plugin is the protocol lab here — this is candidate upstream material, not drift. **Feature divergence: rendezvous** — `WaitingGroupState` answers a hot-joining member's `Ready` with `CompleteHotJoin` and absorbs its `Buffering` (both mirroring `PlayingGroupState`), and its position-correction branch rendezvouses a member that cannot seek accurately rather than re-seeking it, releasing the group with `ResumeIfNobodyElseIsWaiting`. **Fix divergence: a timed-out member's Ready** — `AbstractGroupState.ResumeIgnoredMember` clears `IgnoredByTimeout` for a member that reports ready, called at the top of the `ReadyGroupRequest` handlers in `PlayingGroupState` (after the hot-join branch, whose members carry the same flags deliberately), `PausedGroupState` and `IdleGroupState`. All four states answer a `Ready`, but only `WaitingGroupState` reaches `SetBuffering(.., false)`, which is the only thing that clears the flag; the other three reply with a command and leave it set. Since the wait-timeout sweep runs while the group is Playing, and an ignored member is the one the group will not re-enter Waiting for, upstream it can never be waited for again — contradicting `IgnoredByTimeout`'s own documented contract and `SetMemberDisconnected`'s reliance on it. Upstreamable as-is **Fix divergence: a stall no one waits for cannot hold the group** (#14) — `WaitingGroupState`'s `Buffer` handler calls `RestartWaitFor` for a member the wait timeout gave up on and that stalls again before it ever reports ready: without it the group entered `Waiting` for that member while `IsBuffering()` and the wait-timeout sweep both skipped it, so nothing ended the wait but a second Unpause or a Seek (measured: 25-41 s stuck, jellyfin-web clients). The call sits ahead of the wrong-item check, whose early return would otherwise leave the member ignored in a `Waiting` entered for it. A spectator's `Buffer` is absorbed (`AbstractGroupState.IsSpectatorStall`, over `IsSpectator`) in `PlayingGroupState`, `PausedGroupState` and `WaitingGroupState` instead of entering or extending a `Waiting` it can never leave, and is not recorded as buffering: unlike a hot-joiner's, whose `Ready` runs `CompleteHotJoin`, no `Ready` handler outside `Waiting` would clear the flag. jellyfin-web only sends `IgnoreWait(true)` together with stopping local playback (group menu, media failure), so members following the group never take this path. Upstreamable with the `IgnoredByTimeout`/`IgnoreGroupWaitByRequest` split. **Feature divergence: diagnostics** — `WaitingGroupState`'s two correction branches call `RecordCorrection` next to their existing log line; nothing else about them changes. **Fix divergence: the resume floor is in milliseconds** — when the last member reports ready and the group resumes, `WaitingGroupState` floors the lead at `DefaultPing`, but compared it against a tick count, so the 500 ms floor was 0.05 ms and a LAN group resumed with 2 x ping (measured: "has 0.142 seconds to recover" at a 71 ms ping). The same floor is applied correctly in `PlayingGroupState` and `ResumeIfNobodyElseIsWaiting`. Upstreamable as-is. **Fix divergence: a recovering member is sent the Unpause** (#15) — when the member the group waited for reports ready behind the group, `WaitingGroupState` schedules the resume for when it will have caught up and sent that `Unpause` to everyone except the member if it was already playing; the `Playing` state update that follows still went to everyone, and jellyfin-web answers it with a "schedule-play" indicator that only a scheduled `Unpause` clears, so it stayed over the member's video for good. A v1 member now gets the `Unpause` too: it is behind, so jellyfin-web's `scheduleUnpause` does not seek it (it seeks only a client that is ahead), and `localUnpause` on a playing player is a no-op. A v2 member that is already playing behind the group is excluded: a v2 client (Kofin's `schedule()`) lines its player up on a scheduled `Unpause`'s `PositionTicks` as soon as it arms it, which would jump a member playing behind the group to where the group will be at the resume, before the resume. Both the recovering and late-resume branches use this member-specific filter; the latter previously sent `AllGroup` even when the playing member was only slightly behind. A paused member and a playing v2 member ahead of the group still receive the command. Not upstreamable as-is: upstream has no protocol version to tell the two clients apart. |

New in this directory, vendored from nothing: `Positions.cs` — the position
clamp behind the RunTimeTicks-0 fix divergence, extracted for the same reason
as its sibling below — `ContentDescriptor.cs` and `ContentTable.cs` — the
external-content entries of plan G3.3, validation and the sentinel-keyed
table — and `CorrectionPolicy.cs` — the pure
decision behind the rendezvous divergence, kept out of `Group` because `Group`
cannot be constructed without a server around it and the decision is the whole
of the behaviour. It lives here rather than beside the wire layer because it is
engine logic and belongs in the same upstream PR series. Note that the CI format
job excludes this whole directory (see `.github/workflows/ci.yml`), so a new file
here is not format-gated — this one was checked by hand with `--include`.

Not vendored (reused from the server's shipped assemblies): `PlayQueueManager`,
all request/enum types, `IGroupState`/`IGroupStateContext`, the stock typed
`GroupUpdate` subclasses the states construct (translated to wire at send).
